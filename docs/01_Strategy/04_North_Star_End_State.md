## 1. 为什么需要这份文档

当前项目正在建设 MVP 和 Controlled Prototype，但 MVP 只回答：

- 第一批用户是谁；
- 现在验证哪条最小价值链；
- 本阶段明确不做什么；
- 什么证据可以证明 VS-01 成立。

MVP 不应承担回答“项目最终要改变什么”的责任。本文件补齐长期方向，避免团队在连续交付中只围绕局部功能优化，却逐渐失去对终局的共同判断。

这份文档不是新的 MVP PRD，也不是未来功能清单。它的作用是：

1. 给产品、工程、商业和验证工作提供共同的长期目标；
2. 说明什么样的能力积累才是在接近终局；
3. 为每个阶段提供“继续建设、调整方向或停止投入”的判断标准；
4. 约束远景不能反向扩大当前范围。

## 2. 北极星命题

### 2.1 一句话北极星

> 让每一个能够凭个人身份创造价值的人，都拥有一套独立于社交平台、可发现、可交易、可履约、可持续经营的个人商业基础设施。

### 2.2 终局目标

项目的终局不是成为最大的内容平台，也不是把所有个人变成平台员工，而是成为个人商业关系的基础设施层：

```text
个人身份与能力
→ 结构化供给与可用库存
→ 清晰的商品与商业动作
→ 可信的交易与履约
→ 可持续的客户关系与经营数据
→ 更强的个人收入能力与商业所有权
```

当终局成立时，个人不再需要用社交平台、表格、聊天软件、预约工具、票务工具、收款工具和多个后台拼接自己的经营系统。个人可以像一个小型公司一样拥有并经营自己的商业关系，同时保留对身份、客户、数据和收入的控制权。

### 2.3 北极星不是一句增长口号

本项目真正要优化的不是单纯的注册数、页面浏览量或内容曝光量，而是：

> 有多少个人能够持续把真实能力和真实时间转化为可理解、可购买、可交付并能带来复购或持续合作的商业关系。

因此，任何增长都必须回到真实供给、真实需求、真实交易和真实履约；虚假库存、不可兑现的承诺、不可迁移的客户关系或仅有流量而没有商业结果，都不算接近北极星。

## 3. 终局状态：什么必须成为事实

终局不是某一个页面，而是一组稳定成立的产品事实。

### 3.1 个人拥有商业身份

个人拥有一个可迁移、可验证、可持续维护的 Commercial Identity，能够表达：

- 我是谁；
- 我能做什么；
- 我在哪里以及何时可用；
- 我为谁提供价值；
- 我过去完成过什么；
- 他人如何与我建立商业关系。

该身份属于个人经营主体，而不是某个社交平台账号的附属页面。

### 3.2 个人拥有结构化供给

个人能够把能力、时间、地点、影响力、作品、关系和其他可交付资产组织成结构化供给，并明确：

- 供给是什么；
- 适用对象是谁；
- 何时、何地、以何种容量可用；
- 价格或合作条件是什么；
- 需要经过什么确认；
- 如何完成交付。

Calendar、Storefront、Offering 和 Commerce Action 都是服务于这组事实的产品表面，不是终局本身。

### 3.3 商业动作与履约可被理解

客户不需要通过私信反复猜测“可以买什么、是否可用、下一步是什么”。每一类商业动作都应有清晰的：

```text
入口 → 资格 / 可用性 → 动作 → 状态 → 结果 → 后续关系
```

平台必须能区分请求、预约、购买、雇佣、委托和其他动作的语义，不能把所有行为都降级为聊天或表单。

### 3.4 交易关系可持续经营

一次交易不是终点。个人能够在合规和用户授权边界内理解并经营：

- 客户从哪里来；
- 客户购买过什么；
- 哪些供给带来持续需求；
- 哪些关系适合复购、会员或长期合作；
- 哪些承诺和履约记录影响信任。

这意味着平台的核心资产最终是可解释的 Personal Commerce Graph，而不是不可迁移的流量池。

### 3.5 个人拥有结果与控制权

终局必须让个人获得更强的商业所有权：

- 身份与商业档案可迁移；
- 客户关系不被单一分发平台锁死；
- 经营数据可理解、可导出并受权限控制；
- 平台通过清晰、可持续的价值交换获得收入；
- 平台不以不透明规则夺取个人的商业主体地位。

## 4. 产品终局模型

长期产品可以被理解为五个相互连接的层：

| 层 | 终局职责 | 核心问题 |
| --- | --- | --- |
| Identity | 个人商业身份、能力、证明与信任 | 这个人是谁，能做什么？ |
| Inventory | 时间、地点、容量、可用性与约束 | 什么时候、在哪里、还能接多少？ |
| Commerce | 商品、价格、资格与商业动作 | 客户可以买、约、请或合作什么？ |
| Fulfillment | 确认、交付、变更、记录与结果 | 承诺是否被可靠兑现？ |
| Relationship | 客户、复购、合作、数据与经营反馈 | 如何把一次结果变成持续经营？ |

这五层共享同一套领域语义，但不要求对应同一张数据库表、同一个 API 资源或同一个客户端页面。产品对象、工程模块和平台形态仍应按各自职责演化。

## 5. 从 MVP 到终局的关系

VS-01 是终局的一条窄切片，不是终局的缩小版全量实现。

```text
VS-01
Creator Identity
→ Published Storefront
→ Offering
→ Customer Request
→ Creator Confirm / Decline
→ 可追溯事件与通知

终局
Personal Identity
→ 多类型 Inventory
→ 多类 Commerce Product
→ 交易与支付
→ 履约与信任
→ Relationship / Data / Business Network
```

当前阶段必须坚持：

- 用 Creator 验证“个人商业身份能够承接直接商业关系”；
- 用最小 Offering 和 Request 验证结构化供给优于碎片化私信；
- 用状态、权限、事件和结果验证商业关系的可追溯性；
- 不因为终局包含支付、结算、Marketplace、CRM 或更完整的 OS，就提前把这些能力塞入 VS-01。

任何产品行为变化仍须遵循工程治理中的 `DEV-###` 偏差流程，并由产品决策批准后更新对应事实源。

## 6. 北极星衡量框架

本节定义长期应观察的结果，不把远期数字伪装成当前承诺。

### 6.1 核心结果指标

> **Verified Personal Commerce Relationships**  
> 在指定期间内，由个人发起或承接、经过明确商业动作、产生可验证结果并具备后续经营可能性的真实商业关系数量。

一条关系至少需要满足：

1. 归属于明确的个人 Commercial Identity；
2. 由结构化供给或明确商业动作承接；
3. 具备可追溯的状态变化和结果；
4. 不以测试、Mock、Fixture 或虚构库存计入；
5. 能在授权边界内支持后续履约、复购或合作。

该指标不等同于 GMV、订单数、注册数或页面浏览量。不同阶段可以使用不同的阶段指标，但不能把代理指标误认为终局结果。

### 6.2 四类长期健康信号

| 维度 | 需要证明的事实 | 典型信号 |
| --- | --- | --- |
| 供给真实性 | 个人愿意持续维护真实供给 | 活跃供给、可用库存准确率、过期供给清理 |
| 需求有效性 | 客户能理解并采取正确商业动作 | 合格请求率、动作完成率、无效沟通下降 |
| 履约可信度 | 承诺能够稳定兑现 | 确认后完成率、取消 / 争议率、结果可追溯性 |
| 关系持续性 | 一次结果能带来持续经营 | 复购、重复合作、客户留存、跨商品关系 |

### 6.3 反指标

下列结果不能单独证明接近北极星：

- 只增长不产生商业结果的流量；
- 没有真实可用性的商品或库存数量；
- 个人被迫迁移到平台、但无法带走身份和客户关系；
- 依靠不透明收费、锁定或误导产生的短期收入；
- 只在 Mock、模拟器、Fixture 或本地 Sandbox 中成立的交易；
- 为追求指标而扩大尚未验证的产品范围。

## 7. 战略原则

### 7.1 先承接已有商业意图，再创造新行为

优先降低已经发生的发布、询价、预约、购买、雇佣和合作流程中的摩擦，而不是先建设依赖大规模网络效应的新社交行为。

### 7.2 个人是商业主体，不是库存

平台服务个人经营，不把个人降格为可被平台抽取和替换的供给单元。身份、关系、数据和收入控制权是产品价值的一部分。

### 7.3 结构化优先于复杂化

先让身份、供给、动作、状态和结果被清晰理解，再扩展自动化、推荐、金融或网络能力。

### 7.4 真实履约优先于名义交易

只有能被真实交付、观察和复盘的商业关系，才可以沉淀为长期资产。

### 7.5 平台中立，关系可迁移

社交平台可以继续负责注意力和分发；本项目负责商业承接和关系经营。产品不应要求个人放弃已有渠道，也不应把客户关系永久锁在单一入口中。

### 7.6 每一阶段只建设必要的下一块基础设施

终局用于选择方向，不用于提前实现所有未来。阶段范围必须由当前最关键、可证伪的假设决定。

## 8. 阶段闸门

每次从一个阶段进入下一个阶段，至少应回答以下问题：

| 闸门 | 必须证明 |
| --- | --- |
| Identity | 个人愿意把商业身份和真实能力维护在系统中 |
| Inventory | 供给的时间、地点和容量能够被可靠表达 |
| Commerce | 客户能够独立理解并完成合适的商业动作 |
| Fulfillment | 平台能记录并改善承诺到结果的过程 |
| Relationship | 关系和数据能支持持续经营，而不是一次性导流 |
| Infrastructure | 新增场景可以复用核心语义，而不需要为每个垂直重造系统 |

如果一个阶段只能增加曝光，却不能增强上述任一层的真实能力，就不应被视为北极星进展。

## 9. 明确不追求的终局

本项目不以以下状态为目标：

- 成为替代所有社交平台的超级 App；
- 控制个人全部注意力和内容分发；
- 在没有真实供给和履约能力前建立开放 Marketplace；
- 通过支付、金融或抽佣先行定义产品价值；
- 用一个庞大 ERP 覆盖所有个人经营场景；
- 让个人为了使用基础设施而失去客户、数据或商业自主权。

这些方向未来可能出现为能力或合作，但都不是北极星本身。

## 10. 决策规则

未来任何重大产品、商业或工程提案，都应能回答：

1. 它增强了 Identity、Inventory、Commerce、Fulfillment 或 Relationship 的哪一层？
2. 它是否让真实个人更容易形成可验证的商业关系？
3. 它是否保护个人的身份、客户、数据和商业控制权？
4. 它当前是否有足够证据，还是仅仅因为终局想象而提前建设？
5. 如果不做这件事，是否会阻断下一阶段的关键验证？

若无法回答，提案应保持 Pending，而不是通过扩大 MVP 范围来掩盖战略不确定性。

## 11. 北极星声明

> **我们要建设的不是一个让个人获得更多曝光的平台，而是一层让个人真正拥有、经营并持续增长其商业关系的基础设施。**

Creator 是我们的起点，Personal Commerce Infrastructure 是我们的终点；每个 MVP 都必须同时服务当前验证和未来可复用的个人商业基础。

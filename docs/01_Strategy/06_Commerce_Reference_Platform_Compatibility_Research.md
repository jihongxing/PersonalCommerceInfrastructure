# 06 — Commerce Reference 平台过滤兼容性研究

> **状态**：`PROPOSED RESEARCH`（拟议研究）
> **研究编号**：`PCI-RESEARCH-002`
> **查询日期**：2026-08-26
> **权威**：主控制 / Founder
> **范围**：仅限研究；不构成实现授权
> **阶段**：`STAGE_3 = NOT_AUTHORIZED`

## 1. 研究目标与已批准基线

Founder 已批准以下方向：

```text
Commerce Reference = 18 位大写、人类友好 Base32 方向
规范形式 = 大写字母数字
独立于 URL
公开标识
不可变更
不可复用
默认不可转移
```

本研究验证以下形式在第三方分发平台上的误判风险：

```text
C7K4M9Q2T8W5R3X8Z6
```

本研究的目标是“降低风险”（`RISK REDUCTION`），不是“保证绕过”（`GUARANTEED BYPASS`）。不得声称任何字符格式可以保证
不被平台限制、过滤或人工审核。

## 2. 关键结论摘要

```text
18 位大写受限 Base32 = 继续成立
字符集 = 暂不需要因平台过滤证据而调整
固定语义前缀 = 不建议
规范形式标点 = 继续禁止
大规模子串黑名单 = 不建议
校验位 = 不应为降低平台过滤风险而增加
长度 = 18 位继续成立
平台安全呈现规范 = 必须增加
传播行为控制 = 比字符串本身更重要
```

目前没有取得可信公开证据证明：`C7K4M9Q2T8W5R3X8Z6` 这类单个 18 位随机大写字母数字字符串，
仅因字符串形态本身就会在六个平台被普遍过滤。

```text
该确切形式的字符串级自动过滤
= 尚未建立证据
```

这不表示“绝对安全”。平台可能依据上下文、账户信誉、重复传播、发帖频率、站外导流、外链
声誉、自动化行为和人工审核采取措施。

### 3.3 证据边界

公开官方政策可以支持以下判断：

```text
重复内容、批量行为、自动化、欺骗性导流、恶意链接和账户信誉是重要风险信号。
```

公开官方政策不能支持以下断言：

```text
某一个随机 18 位大写 Base32 字符串一定被接受。
某一个随机 18 位大写 Base32 字符串一定不会被过滤。
某一种字符比例一定会降低平台风控分数。
某一个自然语言标签一定可以避免检测。
```

## 4. 风险信号分层

### 4.1 字符串级过滤

可能被通用系统识别的字符串特征包括：

```text
纯数字
数字 + 大写字母
连续固定长度
固定第一个字符
高熵随机字符串
低熵或重复字符串
特定前缀/后缀
URL、电子邮件、提及、话题标签、一次性验证码、支付码或优惠码结构
```

针对 `C7K4M9Q2T8W5R3X8Z6`，当前公开证据只足以确认：

```text
它不含 URL 协议方案
它不含 @、#、.、/、:
它不是纯数字
它不直接呈现为电话号码
它不直接呈现为电子邮件地址或话题标签
```

以下事项为：

```text
EVIDENCE NOT ESTABLISHED
```

```text
平台是否专门识别任意 18 位大写字母数字随机串。
平台是否把该字符串识别为一次性验证码、支付码、跟踪编号或广告码。
平台是否因为首字符为 C 而提高风险。
平台是否因为数字与字母比例而提高风险。
```

### 4.2 上下文级过滤

上下文可能包括：

```text
“加我”
“搜我”
“联系我”
“去我主页”
“点击”
“私信”
“领取”
“优惠”
“付款”
“验证码”
“返现”
外部 URL
其他平台名称
```

因此：

```text
Commerce Reference 本身 ≠ 导流行为
Commerce Reference + 高压站外指令 = 更高上下文风险
```

自然语言上下文可能帮助用户理解，但不能保证绕过检测。平台安全系统通常可以综合分析文本、
账户、行为、链接和历史信誉。

### 4.3 账户级与行为级风险

```text
账户信誉
行为级检测
链接信誉
```

相同 Commerce Reference 在一个正常账户的 Profile 信息中出现，和在新建账户中短时间复制到
大量评论，风险不能等同。

以下字符串仅用于研究，不代表平台测试结果：

| 测试值 | 形态 | 初步风险判断 |
| --- | --- | --- |
| `C7K4M9Q2T8W5R3X8Z6` | 18 位随机大写字母数字 | 非 URL、非 mention、非 hashtag；字符串级过滤为 `UNKNOWN`。 |
| `A00000000000000000` | 固定首字母 + 大量零 | 低熵、重复、类似测试值/序列值；不推荐。 |
| `000000000000000000` | 纯数字、重复 | 更像占位符、验证码或测试值；不推荐。 |
| `138001380001380001` | 纯数字、电话样式 | 可能被视为电话号码或重复数字；不推荐。 |
| `AB12CD34EF56GH78JK` | 18 位交替分组字母数字 | 类似人工生成代码；不证明比随机值更安全。 |

不能从这些外观比较推导平台实际模型的内部阈值。对具体字符串的实际过滤状态：

```text
除非合法的受控测试或平台官方声明建立证据，否则均为未知。
```

## 6. 语义碰撞分析

### 6.1 可能的误解释

| 类型 | `C7K4M9Q2T8W5R3X8Z6` 的直接相似度 | 结论 |
| --- | --- | --- |
| OTP / 2FA / verification code | 中 | 18 位且含字母，不是典型数字验证码；仍可能被泛化代码识别，证据不足。 |
| Payment / bank reference | 中 | 纯文本代码外观相似；不能排除金融语境误判。 |
| Coupon / promo / gift code | 中 | 受限大写字母数字与优惠码外观相似；标签应明确为商业身份引用。 |
| Tracking / order / ticket ID | 中 | 固定长度 opaque code 可能相似；自然语言应避免“订单、物流、领取”等词。 |
| Phone number | 低 | 含较多字母，不呈现为电话号码。 |
| URL / email / hashtag / mention | 低 | 不含相关特殊字符或 scheme。 |

### 6.2 字符比例

当前示例 `C7K4M9Q2T8W5R3X8Z6` 为 18 位，其中 9 个字母、9 个数字，即约 50/50。

当前没有可靠公开证据证明：

```text
50/50 比例比 70/30、80/20 更不容易触发平台过滤。
letter-heavy 比 digit-limited 更安全。
某种随机分布一定更像自然文本。
```

```text
字符分布影响 = 没有证据
```

因此不应为了“看起来像自然文本”而放弃均匀随机生成。均匀性更有利于容量、不可预测性和
长期稳定性。


### 7.1 单字符审计

| 字符 | 研究判断 |
| --- | --- |

| `1` | 与 `I`、`L` 的视觉混淆；保留可提高容量，但需清晰字体。 |

| `T` | 未发现通用协议或金融关键词冲突。 |

| `Y` | 未发现通用协议或金融关键词冲突。 |

结论：

```text
没有公开证据支持继续大幅删除当前字符集。
```

`0/1` 等字符的排除主要属于人因优化，不是平台风控规避。

### 7.2 短偶然子串是否有实际风险

对于 18 位、32 字母表、均匀随机生成的字符串，任意指定长度为 `k` 的短 token 在任意位置
出现的粗略上界约为：

```text
(18 - k + 1) / 32^k
```

例如：

| 子串 | 长度 | 单个随机 18 位值的近似出现概率上界 |
| --- | ---: | ---: |
| `WWW` / `XYZ` | 3 | 约 `4.88e-4`，即 `0.0488%` |
| `COM` | 3 | `0`；当前 alphabet 已排除 `O`。 |
| `0000` / `1111` / `AAAA` / `TEST` / `HTTP` / `SCAM` / `SPAM` | 4 | 约 `1.43e-5`，即 `0.00143%` |

这是保守上界，不是平台检测概率。它说明短 token 偶然出现并不等于该字符串具有对应语义，
也不应仅凭直觉删除大量字符。

## 8. 子串与模式约束

### 8.1 是否需要黑名单

研究建议：

```text
不建立数千条语义黑名单。
不把 SCAM、SPAM、TEST、HTTP、WWW、XYZ 等偶然子串默认视为违规。
`COM` 因字符集不含 `O`，无需额外禁止。
不禁止所有重复字符组合。
不依靠黑名单声称规避平台检测。
```

可以考虑的最小约束仅限于规范和协议安全：

```text
禁止 canonical 值之外的 @、#、.、/、:、URL scheme 和控制字符。
必要时保留极小、版本化的协议保留词集合。
任何保留词必须有明确产品或协议理由，并记录版本。
```

### 8.2 命名空间损失

对单个固定 token 的粗略上界，18 位 Base32 命名空间损失约为：

```text
4-character token：约 0.00143%
3-character token：约 0.0488%
```

但黑名单成千上万时，损失不能简单相加，因为不同模式会重叠；同时会产生：

```text
熵降低
生成复杂度增加
分布偏差
冲突行为复杂度增加
未来政策维护成本增加
```

因此本研究推荐：

```text
候选 B — CSPRNG + 受限字符集
不推荐候选 C — CSPRNG + 大规模模式黑名单
```

## 9. 前缀研究

| 形式 | 平台文本解析 | 模板化风险 | 品牌识别 | 命名空间 | 结论 |
| --- | --- | --- | --- | --- | --- |
| `C7K4M9Q2T8W5R3X8Z6` | 良好 | 低，示例首字符 `C` 只是随机结果 | 需配合标签 | 18 位全部随机，90 bits | 推荐。 |
| `PC7K4M9Q2T8W5R3X8Z6` | 良好 | 更像固定营销模板或推广码 | 较强 | 若 `PC` 追加在 18 位 payload 前，熵不变但总长增至 20；若占用原 18 位，则减少 `32^2` 倍 | 不推荐。 |
| `PCI7K4M9Q2T8W5R3X8Z6` | 良好 | 更明显的品牌模板 | 强 | 若 `PCI` 追加，熵不变但总长增至 21；若占用原 18 位，则减少 `32^3` 倍 | 不推荐。 |
| `C-7K4M9...` | 连字符可能被解析为分隔符 | 模板明显 | 历史识别强 | 不是 canonical alphanumeric | 仅展示分组，不作规范值。 |

固定 Prefix 是否一定提高广告检测或 spam 风险：

```text
NO EVIDENCE
```

但固定 Prefix 会降低随机空间、增加模板一致性并强化“代码/推广码”外观，因此不值得承担。

## 10. 长度研究

| 长度 | 理论容量 | 1B 随机碰撞概率 | 10B 随机碰撞概率 | 人工传播 | 代码外观 | 结论 |
| ---: | ---: | ---: | ---: | --- | --- | --- |
| 12 | `1.153e18` | 35.19% | 近 100% | 好 | 较短代码感强 | 拒绝。 |
| 14 | `1.181e21` | 0.0423% | 4.147% | 好 | 代码感强 | 不作为长期 1T 方向。 |
| 16 | `1.209e24` | 0.0000414% | 0.00414% | 较好 | 中等 | 1T 余量不足。 |
| 18 | `1.238e27` | 0.0000000404% | 0.00000404% | 好 | 可接受 | 推荐。 |
| 20 | `1.268e30` | 极低 | 极低 | 较差 | 更像机器码 | 仅作额外余量备选。 |

平台是否对 12、14、16、18、20 位分别采用不同过滤阈值：

```text
EVIDENCE NOT ESTABLISHED
```

不能为了“更不像验证码”无限增加长度。18 位是容量、人工传播和平台纯文本兼容性的平衡点。

## 11. 人类呈现研究

### 11.1 规范值

```text
C7K4M9Q2T8W5R3X8Z6
```

适合复制粘贴和机器读取，但单独出现时容易被看作未知代码。

### 11.2 分组值

```text
C7K4M9-Q2T8W5-R3X8Z6
```

适合海报、图片、口述和人工核对；连字符只属于展示格式，不属于 canonical value。

### 11.3 标签值

```text
C号：C7K4M9Q2T8W5R3X8Z6
```

有助于说明它是商业身份引用，而不是 OTP、付款码或优惠码。不能保证绕过平台检测。

### 11.4 自然句子

```text
我的个人商业身份：
C7K4M9Q2T8W5R3X8Z6
```

比单独投放字符串更有语义解释，但仍不能与“加我、点击、领取、付款、私信”等高压导流词
组合成重复模板。

### 11.5 推荐呈现规则

```text
优先：自然语言标签 + Commerce Reference
次选：自然语言标签 + 独立一行的 Reference
允许：图片或海报中的分组展示
避免：单独重复粘贴到大量评论
避免：与外部 URL、短链、优惠、付款、验证码词汇放在同一模板
避免：把 Reference 称为验证码、密钥、兑换码或登录码
```

## 12. 上下文安全与站外导流

YouTube 官方外链政策明确覆盖 URL、图片/视频中的 URL、口头导向其他网站或平台的行为。
其他平台也普遍将欺骗性外链、误导性导流和不真实行为纳入安全治理。

独立于 URL 的 Commerce Reference 可能比 URL 更适合表达 PCI 身份，但不能据此假设它一定
比 URL 安全：

```text
Reference 本身不含 URL 语法，减少了类似 URL 的解析风险。
Reference 仍可能在上下文中成为站外导流的一部分。
Reference + 外链 + 强导流措辞，风险由整体内容和行为决定。
```

因此 PCI 不应使用以下传播模板：

```text
加我，去这个链接，输入 C7K4M9Q2T8W5R3X8Z6 领取优惠
```

建议使用中性、事实性表达：

```text
我的个人商业 C 号是 C7K4M9Q2T8W5R3X8Z6。
```

这只是风险降低建议，不是检测绕过保证。

## 13. 重复传播风险与分发安全规范

### 13.1 同一用户、多个帖子

```text
同一 Commerce Reference
    ↓
同一用户
    ↓
多个帖子
```

如果用户在多个正常 Profile / Description 中维护自己的 Commerce Reference，不能自动等同于
spam。但在短时间内将相同字符串复制到大量无关评论、帖子或私信，可能与重复内容、批量
行为和导流行为共同形成高风险信号。

### 13.2 多用户、多个账户

```text
Same Commerce Reference
    ↓
多个用户 / 账户
```

这可能是合法代理、团队或共享商业身份，也可能看起来像协调网络。平台通常需要依据账户
关系、内容相似度、频率、授权关系和行为历史判断；PCI 不能为平台作结论。

### 13.3 分发安全指南

```text
1. 只在用户控制或获准管理的 Profile、Description、固定评论或宣传材料中使用。
2. 不批量复制到无关用户内容的评论区。
3. 不用自动化脚本、机器人或多账户网络扩大传播。
4. 不把 Reference 与欺骗性 URL、短链、验证码、付款、返现或优惠承诺绑定。
5. 不要求点赞、关注、转发或评论后才能获取承诺内容。
6. 使用自然、准确、低压的身份说明。
7. 同一内容模板不要高频、跨大量帖子重复投放。
8. 记录平台、日期、表面和文案版本，以便发现平台政策变化。
9. 遇到平台限制时遵循申诉和平台规则，不尝试规避检测。
10. 将 Reference 视为公开标识，不能承担认证、授权或付款能力。
```

## 17. 最重要问题：是否需要生成算法层控制？

候选结论：

```text
A — 纯 CSPRNG 已足够
B — CSPRNG + 受限字符集
C — CSPRNG + 受限字符集 + 模式黑名单
D — 带安全约束的确定性分配
```

推荐：

```text
B — CSPRNG + 受限字符集
```

理由：

1. 受限字符集已满足独立于 URL、大写、纯 ASCII、OCR 和人工传播目标；
2. 公开政策没有建立“大写随机字符串本身必然过滤”的证据；
3. CSPRNG 保持均匀性、不可预测性和命名空间容量；
4. 数据库唯一约束与冲突重试解决唯一性，不需要用黑名单代替；
5. 大规模黑名单会带来偏置、复杂度、维护和未来政策漂移；
6. 确定性分配会增加顺序性和枚举风险；
7. 平台风险主要应通过传播上下文和行为规范降低，而不是改造随机字符串来模拟自然语言。

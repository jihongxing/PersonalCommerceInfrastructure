## 1. 目标和完成边界

将用户认可的 Stitch 设计落到现有 `apps/web-v2`，交付一套移动优先的响应式 Web 界面：移动端使用适合触控的布局与导航，桌面端使用对应的宽屏布局；同一业务页面、路由、数据和操作由同一套实现提供。

设计稿是视觉和信息层级的依据。正式应用的数据、可用操作、校验和状态以现有产品合同、已批准决策、真实 API 及经过核实的现有行为为准。原型中的示例人物、固定请求、示例链接和模拟操作不得进入正式流程。

本计划覆盖查找、认证、引导、工作台、资料、对外主页管理、稳定分享工具、能力、服务、访客请求、公开主页、服务详情及请求结果。保持现有 Next.js App Router、React、认证、API 客户端及数据查询体系；按需整理组件，不以替换后端为前提。

本次为未来 PWA 留出响应式与安全区域适配；安装、manifest、Service Worker、离线缓存、推送、原生壳和商店发布均不属于本计划。无新增支付、结算、退款、Marketplace、CRM 或其他未经批准的能力。

## 2. 输入、优先级和现状

1. 先遵守仓库 `AGENTS.md`、冻结的 VS-01 合同、已批准的后续产品决策和偏差；设计稿不能覆盖这些约束。
2. 视觉与布局以 `stitch/shared/app.js`、`stitch/shared/styles.css` 和对应 `code.html` 为准；`stitch/*/*/screen.png` 是旧截图，不能作为当前设计验收依据。`stitch/README.md` 列有页面映射和示例说明。
3. `stitch/web` 和 `stitch/mobile` 是同一响应式原型的两个入口，不是两套独立产品；禁止直接复制原型脚本、模拟状态或 `example.com` 二维码作为生产实现。
4. `apps/web-v2` 使用 Next.js、React、TanStack Query、Radix UI、Tailwind、Lucide 和现有 `qrcode`；优先复用现有能力。`apps/web` 是另一套应用，不作为替换目标。
5. 当前工作树已有 `stitch/` 和执行台账的未提交内容。执行前记录实际状态，不覆盖、重置或清理用户工作；任何新生成截图和证据应采用不会覆盖既有文件的位置。

用户已认可在工作台和主页管理同时显著展示稳定分享工具；现有决策 32 / DEV-065 则规定工作台不展开二维码生成器，只展示轻量摘要。因此，在实现工作台完整分享模块之前：

1. 在执行台账选择未使用的 `DEV-###`，记录冲突、用户已批准的设计方向、范围、受影响 FR / 事件 / 验收与风险；不得预占编号。
2. 形成对决策 32 的明确后续产品决策，写清工作台可以展示稳定分享工具，同时完整主页方案、窗口和发布管理仍留在个人资料区域；以该后续决策明确替代原决策中冲突的工作台二维码限制。
3. 审查复制、下载、系统分享是否仅是界面及浏览器能力，或涉及现有产品行为、事件、权限、分发语义及 PRD 合同。若涉及产品行为变化，按 `DEV-### → 产品决策 → 必要的 PRD 修订 → 实现与验收` 执行；不得自行声称所有变化均为纯样式。
4. 用户对新设计的认可可作为方向授权，不能替代仓库要求的可追溯记录。先核对既有授权与合同；仅在确有未决产品语义时提出具体问题，其余可独立实施的阶段继续推进。

## 3. 产品和工程不变量

- C 号和规范 `/r/{C号}` 地址保持稳定；资料、方案和时间窗口切换不创建新地址。公开主页可能因发布状态或可用性而不可访问，不能承诺永远在线。
- C 号不是身份、资质或平台背书；公开资料与服务继续遵循既有公开字段和权限边界。
- 同一时刻最多一个激活主页；保留发布、暂停、默认方案、窗口冲突、时区与预览规则，以及无公开服务时的既有行为。
- 复制链接、展示或下载二维码以及唤起系统分享，不得被误记为已完成外部分发。现有 `Generated` / `Distributed`、规范事件及记录实际分发的行为，以合同和既有实现为准。
- 保留既有匿名访问、身份恢复、权限检查、令牌访问、表单字段及验证、请求提交和既有状态转换。不得在 UI 中凭空增加终态、伪造列表或暴露其他用户的数据。
- 保留服务发布条件、发布与下架、已有请求处理及错误反馈；服务下架不应抹掉历史请求。
- 不静默修改 API、数据库、状态机、规范事件、授权范围或冻结文档。若实现发现必须变更，先登记并完成适用的治理流程。
- 用户认可的页面外观不是接口可用性或 VS-01 验收通过的证据。所有测试结果写明环境、真实依赖、跳过项与限制。

### 5.0 阶段 0：治理、盘点和可复现基线

- 检查工作树、依赖、Node / pnpm、现有运行服务及端口；确认 API、数据库、认证方式、测试账号和数据隔离方式，不覆盖既有进程和用户数据。
- 完成第 2.1 节决策流程；记录设计确认依据、受影响需求、领域对象、状态、事件、权限及相关验收，不预设无需偏差。
- 对第 4 节全部路由建立功能与状态清单，追踪到具体组件、查询、mutation、接口、既有测试及设计参考；记录缺失和风险。
- 基线运行前端类型检查、构建、相关测试及可行的浏览器流程；记录命令、结果、失败、跳过原因、环境及证据位置。区分既有失败和本次引入的问题。
- 识别当前公开 origin 的配置、认证和测试数据前置条件；用受控测试数据进行写操作。

完成标准：每个路由有清晰的实现与验证归属；决策冲突有记录；基线结果真实可复查。环境不足时记录阻塞并继续不依赖该环境的工作。

### 5.1 阶段 1：设计基础与响应式外壳

- 从原型整理颜色、排版、间距、按钮、表单、状态、焦点和断点，适配现有 `apps/web-v2/styles/globals.css` 与 `components/ui`；复用 `lucide-react`，避免依赖远端图标字体才能操作。
- 重建 Creator 外壳：移动端底部导航、桌面侧边导航、当前页面状态、资料入口及退出登录；保留 `ProtectedRoute`、会话恢复及登出失败反馈。
- 整理公开与认证页面外壳，避免重复页头或嵌套 `main`；确保旧 URL 和 `/profile?tab=public` 继续工作。
- 处理 `viewport-fit`、安全区域、移动底栏内容留白、软键盘、长文本和缩放；不因 PWA 预留而引入离线缓存。

完成标准：在 320px、375px、768px 和桌面视口中导航、表单及焦点可用，无横向溢出或固定栏遮挡；认证保护和退出未回归。

### 5.2 阶段 2：工作台、资料、主页和分享

- 工作台接回身份、C 号和主页摘要的真实查询；保留彼此独立的加载、错误及重试。请求摘要只在真实数据和权限已核实的前提下显示。
- 个人资料及编辑页保留读取、字段校验、保存、错误与返回。两个 Tab 保留 URL 状态、刷新和浏览器前进后退。
- 按原型调整主页管理视觉层级，保留全部现有方案、公开资料、发布暂停、默认、归档、窗口新增编辑和启用禁用、方案及时间预览等能力；清楚区分当前激活、默认、草稿和不可访问。
- 在决策冲突解决后，抽取复用的分享工具供工作台和主页管理使用：从真实 C 号通过现有 `homepageUrl` 计算地址；二维码、可选文本、复制、下载和分享使用同一 URL；无有效地址时明确原因，不显示伪造二维码。
- 生成可扫码的高分辨率二维码；处理剪贴板不可用、二维码生成失败、Web Share 不支持或用户取消。分享动作不表示已实际分发；可访问性提示 C 号不是身份或资质认证。

完成标准：不同资料及时间窗口不改变规范地址；两入口的 URL 与二维码一致；发布状态、错误、所有管理操作和深链接均经真实或明确标注的受控环境验证。

### 5.3 阶段 3：能力、服务和请求

- 更新列表、详情和表单；保留现有字段、校验、能力关联、发布检查清单、发布和下架及其错误处理。
- 请求列表和操作使用现有查询与 mutation，覆盖真实空态、加载、失败、无权限、重复提交或状态冲突；不增加未经支持的标签和假数据。
- 保留确认、拒绝、既有履约相关操作及结果反馈；核对 API 合同及适用产品决策，避免混淆 VS-01 的非目标与后续已批准能力。

完成标准：Creator 可以完成现有能力及服务的管理路径，并处理真实请求；发布条件不足和错误操作有清楚反馈。

### 5.4 阶段 4：公开主页、服务和结果

- 按原型重建 C 号查询、公开主页、服务详情、匿名请求表单及结果页；只渲染公开接口允许的内容。
- 保留 C 号规范化、主页不可访问、服务不可请求、空服务、无效输入、提交中、防重复、提交失败、令牌错误和结果刷新。
- 保留旧服务地址跳转；请求与结果继续使用实际 API 字段、令牌及状态，避免暗示支付、成交或未经确认的履约。

完成标准：访客可以从真实公开入口查看服务、提交有效请求并查看结果；无效或不可用路径不产生错误的业务结果。

### 5.5 阶段 5：认证和新用户引导

- 改造登录、注册、忘记密码、重置密码和欢迎页；保留现有验证、认证提供方行为、跳转、会话恢复及错误提示。
- 修复阶段 0 确认的引导路由问题；验证登录后目标、未登录访问受保护页面和过期会话的处理。

完成标准：新用户与已有用户可完成真实认证路径；异常不被伪装成成功，深链接和受保护页面权限不回归。

### 5.6 阶段 6：整体回归、清理和交付

## 6. 分享工具专项合同

1. 输入来自已分配 C 号及经过验证的 `NEXT_PUBLIC_WEB_ORIGIN`；沿用 `apps/web-v2/lib/public-homepage.ts` 的 URL 构造和生产 HTTPS 检查，不从当前页面或硬编码域名猜测生产地址。
2. 原型二维码仅为示例。正式二维码由真实 URL 动态生成；复制文本、二维码解码值、下载内容和系统分享 URL 必须一致。二维码下载需要足够清晰、留有静区，并提供可访问名称。
3. C 号未分配、origin 缺失或无效、生成失败、复制失败、浏览器不支持分享均应显示可理解的状态和恢复路径；可选取的地址不能被错误消息替代。

## 7. 跨页面状态与设计验收

每个适用页面至少检查加载、成功、正常空态、请求失败与重试、认证失效、提交中、提交失败以及权限不足；有状态的业务页面还须覆盖合法状态与非法或过期路径。接口失败不得显示成空数据。

视觉验收以当前原型为参考，在同一视口核对导航、信息顺序、间距、颜色、字重、主要操作和固定底栏；未画出的真实功能需保持一致设计语言。检查 320px、375px、768px、1280px 及以上桌面，长内容与 200% 浏览器缩放；不能有横向溢出、截断关键文本、内容重叠或交互被固定栏遮挡。

交互验收覆盖键盘顺序与可见焦点、语义结构、按钮名称、字段标签及错误关联、状态通知、颜色对比、移动触控目标和无悬停依赖。检查移动浏览器安全区域、键盘弹出以及网络慢或中断下的可用反馈。

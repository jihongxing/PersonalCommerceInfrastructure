## 2. D05 — Transaction / Order Abstraction

### 2.1 要解决的系统问题

同一次采购可能同时包含设备、安装或授权，涉及多个 Provider、代付及不同执行进度。需要让六类供给进入同一可追溯交易基础，而不是仅在页面拼接六套订单，也不能用一个通用 Order 的状态覆盖各域。R §7、§16 D05；T07、T09–T12、T15。

### 2.2 关键概念和边界

Commercial Transaction 表达商业交换及关联上下文，区别数据库事务与 Financial Transaction。Order 是采购事项的业务记录/工作边界，不能仅凭名称推出单一合同、付款或承诺。持续 Offering、具体 Proposal / Terms、有效 Acceptance 也分别解释。

可共享的是**事实的关联与可追溯含义**：稳定交易引用、参与主体及上下文角色、供给/条款版本、谁以何种有效方式接受哪个范围、金额/币种/数量或范围单位、后续变化来源。这里不是共同字段清单或写入职责决定。

服务安排、Goods 数量交付/退货、Program 报名参与、Membership 期间续期、Project 范围/验收、Right 授予/期限留在专业领域。领域订单通过有命名空间的稳定引用关联共同交易语境；一次采购可关联多个领域记录，但不预先冻结全局关系基数或每域必须有名为 Order 的实体。

### 2.3 候选方案

| 方案（R §7.2）                                                 | 优点                                                                  | 代价及失败边界                                                                        |
| -------------------------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| TX-A：Universal Order                                          | 单一业务记录下统一操作和展示；某个有界、同接受/取消规则的订单域可适用 | 跨期间、多责任、独立验收会迫使核心吸收领域规则；不能从 T01/T02 推广到六类             |
| TX-B：Shared Transaction Envelope + Domain Transaction Objects | 共同成交事实集中，专业履行独立，组合与金额关联明确                    | 必须证明共同事实为何需要集中写入；条款/金额双重权威或 Envelope 越权会退化为超级 Order |
| TX-C：Domain Orders + Shared Reference / Projection            | 专业写入权威明确，对旧系统侵入较低                                    | 需要共同协议、历史关联及投影治理；只拼页面不能提供真实共享接受/金额事实               |

### 2.4 Main Controller 推荐方案（待审稿）

整理 R §7.4 与 §16 D05：推荐**共同交易引用及接受/参与/金额历史可追溯，专业交易记录独立**的概念方向；窄 TX-B 仍作为需证明职责的候选，以 TX-C 为对照。若没有共同接受、分配、历史集中写入的充分依据，保留 TX-C 方向。

本轮可以请 Founder 判断是否接受这一方向及条件，不能借 D04 的共享引用批准 TX-B 可写封套，也不能在这里确定 Shared Core 的具体写入权威。后者与 D10 相关，继续 DEFERRED。

### 2.5 推荐理由

T07 的设备交付与安装共享一次采购/分配来源，却不共享完成条件；T12 的 Buyer 与 Payer 不同，单 customerId 不足；T14 要还原接受时版本，不能查当前 Offering 替代。TX-B/TX-C 都可表达，差别在事实写入与关联治理，R 尚未证明必须采用某种存储结构。

### 2.6 若采纳后的概念级影响

后续领域定义需说明共同引用、参与者、接受版本与专业记录之间的来源关系；组合视图可以解释每项状态来自哪个域，不能伪造统一成功。现有 VS-01 Request 只按原语义保留来源关联，不补造订单、价款或采购事实。

### 2.7 明确不代表什么

不批准统一 Order / Transaction 表、可写 Envelope、API/DTO/事件、固定基数、跨域原子接受、状态机或代码。未选择 SYS-B 架构，不启动 TX-B / TX-C 原型或 D12 验证，不改变 VS-01。

### 2.8 仍需 Founder 决定的问题

1. 是否批准共同交易事实与专业订单/交易语义分离的概念方向？
2. 是否保留“窄 TX-B 需证明集中职责、TX-C 为对照”的条件性推荐，还是只先冻结共享引用/历史原则？
3. 是否明确将共享写入权威、订单对象及基数留待后续有界裁决，而不在本轮决定？

## 3. D06 — Order and Commitment

### 3.1 要解决的系统问题

一笔采购可能产生服务执行、分批交付、期间权益、阶段验收和权利授予等不同责任。如果一 Order 等于一 Commitment，再用一个 Fulfilled 终态概括，会丢失部分履行、参与方责任及变更依据。R §7.1、T04/T05/T14/T15、§16 D06。

### 3.2 关键概念和边界

**Order、Commitment、Fulfillment、Payment 保持语义独立。** FD-F01 已定义 Commitment 为相应领域有效接受机制形成的责任或权益事实；并非每个 Request 都成立承诺。

同一 Order / 采购可以关联多个 Commitment，也可能包含不需拆为独立承诺的多项内容。颗粒度取决于有效接受、责任主体、范围及可独立变更性，不由订单行数、SKU 数、付款次数机械生成。阶段、部分完成、取消及补救必须归属于明确的责任/权益范围；不规定每阶段独立 Order 或独立聚合。

### 3.3 候选方案

| 方案（R §16 D06）               | 优点                               | 代价及失败边界                                         |
| ------------------------------- | ---------------------------------- | ------------------------------------------------------ |
| 一单一承诺、一套履行终态        | 简单一次性交付容易解释             | 多阶段/多主体/期间权益失真；局部完成会被全局状态覆盖   |
| 可多项责任/权益事实，由领域解释 | 保留接受主体、范围、阶段与变更来源 | 关联和摘要解释更复杂；必须防止每订单行自动成为独立合同 |
| 全局独立 Commitment 聚合        | 形式上便于共同管理                 | 实体和共同生命周期未经证明，容易与领域事实重复或越权   |

### 3.4 Main Controller 推荐方案（待审稿）

整理 R §16 D06 第二项：允许一次采购关联多个可解释的责任/权益事实，由领域有效接受及专业规则决定成立、颗粒度和履行依据。保留 Order、Commitment、Fulfillment 的语义区分，暂不决定 Commitment 是否独立持久化或具有全局状态机。

### 3.5 推荐理由

T04 的本期会员权益与未来续费授权不同；T05 的 M1 已验收不会因 M2 变更被重写；T15 的摄影、打印、许可可有不同主体与履行时点。T14 的新条款须有新接受依据，不能以 Offering 最新版静默覆盖历史责任。

### 3.6 若采纳后的概念级影响

后续领域说明应能够回答“谁因哪个有效接受，对谁在何范围承担何种责任或权益”，并关联部分进度、完成与变更事实。共同进度只能是有来源的摘要，不用订单一个布尔值代替履行。保留已完成范围的历史，不因后续取消/退款认定其从未发生。

### 3.7 明确不代表什么

不建立全局 Commitment 实体、不固定一对多数据库关系、不自动产生法律合同，不统一六域履约。既有 Creator Confirm / Decline、Fulfillment Code / QR / Fulfillment Confirmation 保持原合同，不追溯改义 Request confirmed，不新增必需步骤或自动履约。

### 3.8 仍需 Founder 决定的问题

1. 是否明确接受 Order / Commitment / Fulfillment 语义独立、一次采购可关联多个责任事实？
2. 是否接受按领域有效接受及可独立变化的责任范围解释颗粒度，拒绝“一订单行一承诺”的全局规则？
3. 是否将具体领域有效接受、责任变化规则和持久化对象留待各域合同，而不是本轮统一冻结？

## 4. D07 — Financial and Ledger Boundary

### 4.1 要解决的系统问题

代付、分期、合并付款、多 Provider 分配和部分退款，需要共同资金事实及账务追溯；若六域各记真实款会双记，若共享账本决定所有结算条件又会吞并领域规则。R §8、T05/T07/T10–T12、§16 D07。

### 4.2 关键概念和边界

Payment / Collection、Financial Transaction、Financial Obligation、Allocation、Ledger / Entry 与 Balance 必须分别解释。应收/应付是义务的相应方视角，不等于已到账；余额是按 Holder、币种、账户、时点及口径形成的投影，不是可随意修改的总数。

候选共享范围是资金尝试/确认、来源凭证、原款/退款关联、逻辑分配、费用依据和账务历史追溯。领域/有效条款解释谁向谁因何应付、阶段/期间义务、履行依据与释放/结算条件；共享金融基础负责共同资金和账务一致性，不能因回调成功创造验收或 Grant。

退款业务依据、实际退回资金和账务反映分开关联。Settlement 的商业释放判断与机构清算同名但不同；现有 S09 非银行清算，现有 Creator Earnings Ledger 也不是已证明的全球总账。R §8.1–§8.4。

### 4.3 候选方案

| 方案（R §8.4）                                            | 优点                                      | 代价及失败边界                                                             |
| --------------------------------------------------------- | ----------------------------------------- | -------------------------------------------------------------------------- |
| FIN-A：Shared Financial Account + Ledger                  | 全局主体/币种账务与余额一致，便于统一核对 | 若账户归属未定就做一个钱包，会混合身份和资金责任；不能过早成为全套会计系统 |
| FIN-B：Shared Transaction-linked Financial Records        | 按交易关联支付/退款/分配，兼容既有证据    | 流水不足以表达跨交易应收、余额与守恒，不能替代完整账务                     |
| FIN-C：Domain Financial Subledger + Shared Financial Core | 领域义务明细清楚，共用真正资金和核对      | 若各域明细账也各记真实款/余额，会双记并分裂；调整关联更复杂                |

### 4.4 Main Controller 推荐方案（待审稿）

整理 R §8.4 与 §16 D07：推荐**共同金融事实与账务追溯＋领域义务及触发依据**，结合 FIN-A / FIN-C 的概念优点；FIN-B 可作为既有记录的兼容思路。不是同时建立三套账本。

同一真实资金事实不得因域数或重试重复入账；分配总额、累计退款及释放不得超越对应来源和可用范围，按币种保持可解释守恒；纠错保留原事实并追加调整。账户归属、会计口径和技术账本仍未决定。

### 4.5 推荐理由

T07 中 CNY 1000 按已接受依据分为 Goods 700 / 安装 300；安装取消并退 300 不抹除商品交付或原支付。若安装收入已释放，还需独立解释追回/抵扣，不能改原支付金额。此为 R §8.3 既有概念反例，不批准真实退款、追偿或费率。T05/T12 同时否定“一订单一款”和“付款人即买方/受益人”。

### 4.6 若采纳后的概念级影响

后续领域定义应提供可追溯的应付/应收依据与触发事实，金融事实关联这些依据及组成范围；共享金额不能被多个域重复认领。余额、收入权益、已收款、可释放和可提现分别解释。费用、税、折扣、汇率、舍入规则尚缺时不得默认为零。

### 4.7 明确不代表什么

不决定 Account Holder、Identity 一对一钱包、资金托管、双重记账或会计政策，不新增金融表、支付接口、分录、费率或改唯一约束。S07 真实路径 Pending 与 S08/S09 既有有界决定保持原范围；本建议不启用 Payment、Settlement、Refund、Payout 或真实资金活动。

### 4.8 仍需 Founder 决定的问题

1. 是否接受共同资金/账务事实与领域义务/结算依据分离的方向？
2. 是否接受按来源、币种和范围追溯分配、退款、纠错的概念原则，而不批准实际资金流程？
3. 是否将账户责任归属、会计/费用/汇率规则、Provider 路径及写入模型留待单独裁决？

## 5. D08 — Review and Reputation

### 5.1 要解决的系统问题

企业采购者可能不是实际参与人，持续会员和阶段项目也没有同一种评价窗口。需要共享可追溯评价证据，保留评价对象、关系、维度及尺度，避免一次体验重复计权或全局星级平均。R §9、T03/T04/T05/T10/T13、§16 D08。

### 5.2 关键概念和边界

Review 是有作者、对象、语境及修订历史的评价内容；Rating 是按特定版本尺度进行的测量；Reputation 是选择证据、权重、时间口径得到的投影。三者不能合一。

候选共享证据包括来源交易/组成范围、实际参与/履行依据、作者与对象、修订及处置来源。领域保留评价关系、资格、窗口、维度和版本尺度。Goods 产品与配送、Service 执行与 Provider、Program 批次体验、Membership 期间、Project 阶段、Right 授予办理/使用体验都需分别解释，付款不自动证明实际体验或权属。

### 5.3 候选方案

| 方案（R §9.2）                                                | 优点                                               | 代价及失败边界                                   |
| ------------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------ |
| REV-A：Global Review + Domain Dimensions                      | 窄共同作者/对象/证据/版本/处置可复用，维度由域解释 | 不能要求所有域相同星级、资格或完成门槛，否则失效 |
| REV-B：Domain Reviews + Shared Reputation Projection          | 领域内容生命周期最独立                             | 证据、修订与争议治理重复，同一来源可能重复汇入   |
| REV-C：Shared Evidence & Moderation Protocol + Domain Records | 较少内容耦合，仍共享证据与处置协议                 | 协议过薄退为六套，过厚又替代领域内容定义         |

### 5.4 Main Controller 推荐方案（待审稿）

整理 R §9.2 与 §16 D08：优先保留 REV-A **窄共同评价事实＋有类型/版本的领域维度**这一待裁决方向；若持续会员体验或项目争议不能共用内容生命周期，则保留 REV-C。Reputation 应作为评价证据之上、带上下文和口径的独立投影概念，不是原始权威评分，也不据此创建独立实体。

### 5.5 推荐理由

T03 的企业 Buyer/Payer 与学员体验不同；T04 每月付款不能自动生成新评价；T05 阶段及最终评价可能重复同一体验；T10 不应把多个实际 Provider 的评分全部归给发布账号。R §9.1 明确 Review / Rating / Reputation 区别，并要求对象与证据可追溯。

### 5.6 若采纳后的概念级影响

跨域可共享评价来源与历史，按各域资格/尺度呈现；同一 Review 可用于多个带规则的投影，但必须可解释来源及防重复口径。不能把不可比维度直接换算为单一全球分。退款、退出或 Offering 下架不应无痕覆盖体验事实；公开呈现与证据保存不是同一处理。

### 5.7 明确不代表什么

不建立 Review 模块或全球信用分，不冻结自评、Buyer 评价、评价窗口、删除/隐藏、申诉、权重和可见性规则，不默认公开历史私有数据。当前 Policy `review_required`、UI 二次确认中的 review 不是客户评价数据，不做迁移或新增评价入口。

### 5.8 仍需 Founder 决定的问题

1. 是否批准共享证据/追溯、专业维度/资格留域的方向，并保持 REV-A 条件性优先、REV-C 备选？
2. 是否明确将 Reputation 定义为有规则的独立投影概念，拒绝跨域星级直接平均？
3. 是否将资格、窗口、Buyer 评价、自评、可见性及处置规则留待后续有界产品决定？

## 6. D09 — Composite and Cross-Domain Transactions

### 6.1 要解决的系统问题

Service + Goods + Right 可一次采购，却涉及不同 Provider、接受/授予条件和履行阶段。需要表达共同采购及多责任关联，并保留部分履行、局部取消和退款事实，不能以一个组合状态掩盖各域。R §10、T07–T11/T15、§16 D09。

### 6.2 关键概念和边界

R §10.1 将组合区分为**供给、提议、交易、履约、资金**五层，各层不必边界相同。同购不必新建一个长期 Offering；一个组合提议可关联多个供给，一次接受不证明单一合同/Provider，一次付款不证明共同资金所有权。

组成供给保持定义和版本，已接受条款记录各责任主体、范围、价格/折扣与分配依据。多 Commitment 按责任及有效接受解释，不按 Bundle 行数生成。分阶段与部分履行通过具体范围关联；取消未来范围、退货/补救、资金退款和账务调整分开。

### 6.3 候选方案

| 方案（R §10、§16 D09）        | 优点                                 | 代价及失败边界                                                  |
| ----------------------------- | ------------------------------------ | --------------------------------------------------------------- |
| 全部合并一个 Offering / Order | 统一页面和单状态简单                 | 独立责任/版本/完成被吞并；默认全有全无无法解释部分完成          |
| 五层有类型关联，各域责任独立  | 同时表达共同采购、专业履行和金额追溯 | 协调更复杂，必须说明整体/局部条款及金额依据，不能靠包裹名称解决 |
| 只给多个独立链接              | 各域侵入小                           | 共同接受、分配、历史及组合责任缺失，只是拼接购物体验            |

### 6.4 Main Controller 推荐方案（待审稿）

整理 R §10 与 §16 D09：推荐**五层可不同边界、组成版本/责任/分配可追溯的关联组合方向**。各 Provider 对其有效承担的范围负责；共同采购引用可连接多个责任事实，保留领域状态权威。

局部失败不删除其他已成立事实。整体是否不可分、依赖如何影响后续阶段、局部取消及退款依据必须由具体组合条款及领域规则解释，不能在共享层默认为全部成功、全部取消、均分收入或按天退款。

### 6.5 推荐理由

T07 的商品签收不完成安装，安装取消也不删除签收；T08 的课程结业不使会员权益消失；T09 的样品签收、项目验收和许可生效不同；T10 明确多责任方；T11 可同时存在 A 完成 / B 取消 / C 待履行。T15 证明同次采购与 Commitment 数量无机械对应。

### 6.6 若采纳后的概念级影响

组合摘要必须能还原组成版本、参与方、接受范围、各域进度、资金来源和分配依据。局部取消只作用于被有效变更的范围；已履行事实仍保留，退款记录关联相应依据与原款，不反向伪造领域未履行。整体效果与后续依赖仍按明确条款解释，不建立全局状态机。

### 6.7 明确不代表什么

不决定 Bundle / Package 独立实体、统一组合订单、分布式事务、锁、编排或 API，不启动部分退款、取消或补救功能。组合不产生平台担保、自动履约、共同法律责任推定，也不突破既有 VS-01 功能范围。D10 的具体聚合与协调职责继续 DEFERRED。

### 6.8 仍需 Founder 决定的问题

1. 是否接受五层组合可有不同边界、专业责任和状态不因组合而合并？
2. 是否接受组成版本、责任、金额分配及局部变化必须可追溯，禁止以局部失败覆盖全部历史？
3. 是否将整体接受/取消/退款策略交给具体组合合同另行决定，并暂不裁决 Bundle 实体或协调实现？

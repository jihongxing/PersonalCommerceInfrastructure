## 2. D10 — Shared Core and Domain Authority Boundary

### 2.1 要解决的系统问题

共同商业事实不能被拆成六套互不相通的身份、交易关联、资金追溯和评价证据；领域规则也不能被一个具有所有写入权限的 Shared Core 吞并。需要先回答语义上谁负责解释什么事实、哪些结果只能引用，不能先决定聚合、表或服务数量。R §3、§6、§11及 §16 D10 提供原始比较，D01 / D03 / D05–D09 限定本轮答案。

### 2.2 关键概念与责任边界

以下是**概念责任矩阵，不是数据库、接口或写入设计**。

| 概念类别 | 应承担的语义职责 | 必须保留的边界 |
| --- | --- | --- |
| 共享引用 | 稳定识别身份、商业供给和交易关联，使不同领域事实可寻址、可追溯 | 引用不证明所有权、资格或授权；不决定 Owner Anchor 或共享可写对象 |
| 共享事实 | 跨领域具有独立意义的资金及账务追溯、评价证据和来源关联 | 保留真实来源、版本与纠错依据；不凭共享标签制造收款、评价资格或履约事实 |
| 领域事实 | 有效接受及其责任/权益、服务执行、商品交付、Program 参与、Membership 期间、Project 验收、Right Grant | 专业领域解释成立、变化及完成；共享进度不得反向覆盖或替代 |
| 领域投影 | 将领域权威事实按明确语义呈现在共同查询、采购关联或进度摘要中 | 标明来源、版本及未知/延迟；摘要不是第二份可独立编辑的领域真相 |

“共享”不是“只能复制领域状态”。资金来源、金额分配、账务纠错、评价证据及规则化投影具有自身跨领域意义，不能全部塞回 Service 订单状态；但哪些事实由哪一具体组件独立产生、记录或接受外部来源，仍需后续设计授权。支付提供方的原始确认与 PCI 的资金关联/追溯也不能混为同一事实，原始签发来源必须保留。

共享层可以承担这些事实的关联、追溯和共同表达责任；这**不决定**交易上下文必须可写、必须只读，也不批准任何统一交易聚合。领域接受、履行、取消条件、应收应付依据、结算触发及评价资格仍由相应领域解释，D07 / D08 的共享证据不能反过来定义这些规则。

防止超级聚合的概念判据：若每次会员权益使用、项目阶段验收或 Right 使用都必须由全局核心定义成功，职责越界；若同一接受版本、付款或交付在两处能够独立改成不同事实，出现双重权威。避免六套基础设施的判据：同一身份、同笔资金和同份评价证据跨域引用时可追溯且不重复创造，而非要求它们写入同一个表。单事实权威不等于单数据库聚合。（R §8–§11、T04 / T05 / T09 / T12 / T15。）

### 2.3 候选方案

| 候选 | 价值 | 局限及本轮约束 |
| --- | --- | --- |
| SYS-A：统一交易聚合 | 集中表达共同采购，初期路径直接 | 易统一专业状态；Universal Order 与领域语义压缩不符合 D03 / D05 / D06，不能作为当前方向 |
| SYS-B：窄共享事实＋独立领域 | 共同证据与专业执行有清楚分工 | 写入边界不清会成为超级核心；R 的条件性推荐不等于已批准 TX-B 或任何聚合 |
| SYS-C：领域交易＋共享关联和投影 | 保留领域权威，兼容侵入可较小 | 若误作纯页面拼接，会重复身份/资金/评价；也未被 D05 最终选定 |

以上沿用 R §11 候选用于解释边界，并非重新选架构。SYS-B / SYS-C 的实现取舍继续开放。

### 2.4 Main Controller 推荐方案（待审稿）

建议冻结**共享事实职责＋专业领域权威＋有来源的投影**三项原则，而不批准 SYS-B / SYS-C 的具体结构。共享引用、交易关联、资金追溯和评价证据应协同且避免六份重复；专业接受、责任成立和履行事实由领域解释；共同视图只反映有来源的结果。不得由“Shared Core”名称推出所有业务写入权。

对“共享层是否只关联读取”的建议答案是：不能对所有共享能力一概限定只读，因为 D07 / D08 已承认共享资金和评价证据的独立意义；也不能因此批准可写交易封套。独立共享事实的具体生产者、写入职责和接入方式保持未决。

### 2.5 推荐理由

该建议直接延续 D01 / D03 / D04，满足 D05 的领域交易权威、D06 的领域责任、D07 的不重复入账、D08 的证据共享和 D09 的局部事实保留。R §11.3 的失败条件说明：核心需要理解每次权益使用则过宽；各域各记余额或信誉则共享不足。先冻结可检验的责任原则，比先选 Envelope 更符合现有批准边界。

### 2.6 若采纳后的概念级影响

未来每份有界设计应能指出引用、真实事实来源、领域解释者及投影的区别，并能解释纠错或来源变化如何被追溯。跨域采购可以查看共同关联，不据此制造全局完成状态。新领域不应为同一用户、付款、评价证据另造独立真相。此要求只是后续设计的审阅标准。

### 2.7 明确不代表什么

不选数据库聚合、部署拓扑、事务边界、服务数量或消息协议；不决定 Shared Core 的具体写入权、表结构、对象基数、事件/DTO/API；不批准 TX-B、TX-C、统一 Order/Commitment、钱包或评价产品。不启动抽取、适配、双写、编排或迁移。

### 2.8 仍需 Founder 决定的问题

1. 是否采纳上述四类概念的区分及共享职责/领域权威原则，保持实现选型开放？
2. 是否认可共同进度只能是来源明确的投影，不能成为领域成功的另一权威？
3. 是否认可资金追溯与评价证据的共享意义，同时将其具体产生和写入职责留给另行授权的设计？

## 3. D11 — VS-01 Compatibility and Evolution

### 3.1 要解决的系统问题

全球概念不能回头改写已经冻结并实施的非支付 Service 流程、安全边界和历史标识。需要确定 VS-01 的概念定位及演进约束，不能通过新词汇将现有 Request 转成 paid Order，或把 Fulfillment Code 转成全球统一履约状态。依据 R §12 C01–C18、§15、§16 D11，以及现行 PRD 和正式修订。

### 3.2 关键概念与兼容边界

必须分别解释四层：

| 层次 | 当前效力 | 不得混入的含义 |
| --- | --- | --- |
| 已冻结 VS-01 合同 | PRD、正式修订、Creator 安全边界及历史语义继续约束当前实现 | 不因全球 Capability 可选而绕过现有受控发布链 |
| 未来共享关联 | 可以研究稳定引用、来源及兼容关联的概念方向 | 不是新接口、共享写入或迁移已经获批 |
| 未批准产品行为 | 新领域接受、付款、评价或组合流程需另行产品授权 | 不以全球原则改变现有 Creator / Customer 操作 |
| 未批准工程迁移 | 标识映射、适配、数据切换、回退均需单独方案及验证授权 | 不以“兼容”名义直接实施双写或历史补造 |

当前必须保持的事实：

- **Request / 决策**：保留 draft / submitted / confirmed / declined 原有语义及允许的转换；Creator 对 submitted 请求作 Confirm / Decline，不能新增撤销或强制付款步骤。不能把每个 Request 自动解释为全球 Commitment。
- **履约修订**：FD-020-BD-01 保留新 Request 的 Fulfillment Code 生成、Public Result 展示、QR 及 Creator 履约确认。Creator Confirmed / Declined 与 code 的 pending / fulfilled / expired 分开；确认要求所属 Creator、已 confirmed Request、匹配且有效的未核销 code。QR 编码不是授权或履约完成证明，不改写历史结果。（PRD 的 FD-020-BD-01 Amendment。）
- **安全**：Creator 私有请求继续同源 BFF，HttpOnly Opaque Session Cookie、PostgreSQL Session、服务端加密凭据、Refresh CAS、CSRF / Origin 及上游注销撤销语义保持；不在浏览器持久化 Token，不复用 Operations 身份或 Session。本材料引用现有合同/验收记录，不宣称本轮重新运行安全验证。（R §12；本次指令 §3 / D11。）
- **身份与标识**：历史 creatorId 保持原命名空间，不能当作全球 Owner ID；C-number 是 Identity 持有的公开商业引用，非凭据；Identity 可有多个 Profile，不由 Profile 或发布账号推断所有权。匿名请求联系人不能仅凭 email 被自动转成已认证 Customer Account。（Decision29、FD-F04、R §4 / §12。）
- **服务与配置**：受控 Capability / Template、发布门禁及 FD-020-C3-BD-01 限定 Appearance 继续有效。全球不强制 Capability 不取消 VS-01 的能力链。相邻 PaidServiceOrder 有界实现不能被当成非支付 VS-01 已启用支付的依据。（R §12；PRD 正式修订。）
- **历史连续性**：历史 Request、Offering、Fulfillment、标识和有效条款不被改写；未来关联遇到缺失的历史条款应标未知，不能用当前 Offering 补造过去版本。（R §15.2。）

### 3.3 候选方案

| 候选 | 价值 | 风险 |
| --- | --- | --- |
| 路线 A：一次性全球重写 | 名称和页面可快速统一 | 历史补造、身份/状态破坏及大范围回归，现无授权 |
| 路线 B：有界共享提取与兼容适配 | 旧义连续，逐项证明共同性 | 可能仍是 Service 偏置抽象或隐藏双写，提取本身须另行授权 |
| 路线 C：异质领域并行关联 | 用专业差异验证共享边界，少侵入旧流程 | 易重复基础设施及协议漂移，新领域也未获实施授权 |

沿用 R §15.1 / §16 D11。将 VS-01 改定位为隔离的历史产品不能代替兼容分析，也不符合避免六套孤立基础设施的目标；这不是本材料推荐方向。

### 3.4 Main Controller 推荐方案（待审稿）

建议将现有 VS-01 理解为**全球 Service 领域的现有实现切片**，而非被退役或割裂的历史产品；这是本轮待裁决的定位，不追溯改写旧 PRD。保留当前合同，未来在明确授权下采用渐进式关联、兼容适配与异质场景反证，即 R 的 B+C 概念方向。先证明真实共同性，再讨论提取；不得先建统一核心再强迫旧流程迁入。

### 3.5 推荐理由

该方向与 D01–D04 的共享基础/独立领域、FD-F02 的 VS-01 特例约束及 D05–D09 的专业权威一致。R §15 已揭示大爆炸迁移风险、共享提取的 Service 偏置和并行扩展的重复风险；保留旧系统可继续工作与历史未知项，能避免用新模型伪造旧事实。

### 3.6 若采纳后的概念级影响

未来方案应列明旧合同、拟新增关联、拟改产品行为、拟迁移数据四份边界，不将同一项混写。稳定引用可关联旧事实，但新名词不改变旧事实；适配应证明原有决策、核销、权限、身份及来源连续性。每阶段都须有独立授权、退出条件和旧流程可继续运行的证据。

### 3.7 明确不代表什么

不修改 PRD、VS-01 状态机、Capability 门禁、Appearance、Fulfillment 或 Session；不改 creatorId / C-number、不创建客户账户、不选 Owner Anchor；不增加 API、适配器、读视图、事件、迁移或新业务入口。B+C 不是工程路线已经立项，更不是退出当前 VS-01 或启用 Paid Service、资金、外部试点的批准。

### 3.8 仍需 Founder 决定的问题

1. 是否采纳“现有 Service 实现切片，保留原合同”的定位，而非独立历史产品？
2. 是否采纳有界渐进关联与兼容适配的概念方向，保留 B/C 具体方式待设计？
3. 是否将历史语义、未知信息不补造和 Creator 安全边界连续性作为未来演进的必要审阅条件？

## 4. D12 — Minimal Conceptual Validation Instance

### 4.1 要解决的系统问题

再次验证单 Service 不能暴露六域差异；直接使用最复杂组合则难定位失败。需要用最小既有场景识别 D01–D09 的语义是否自洽，并声明其不能证明全部六域、运行安全、账务实现或生产可用。本轮只准备对象与判据，没有执行静态样本推演、原型或工程验证。依据 R §7.3、§15.2、§16 D12。

### 4.2 关键概念与现有场景边界

建议主对象为 **T07 Service + Goods**，叠加 **T12 Buyer ≠ Payer**、**T14 Proposal 改版**；用 **T04 Membership 续期**、**T05 Project 阶段验收**作反例。均来自既有场景，不新增产品类型或交易流程。T10 / T11 / T15 仅作已有多 Provider、局部失败、多责任事实的交叉检查，不能据此扩大为新一轮全场景研究。

R T07 的设备卖方甲、安装 Provider 乙、Buyer 丙，总额 1000 元（设备 700 / 安装 300），以及安装取消按接受分配关联退款 300，是**假设性的概念材料**，不是实际支付、退款或启用 VS-01 资金功能。该金额说明沿用原场景，不新增数值价格模型。T12 的代付不改变 Buyer、受益人和领域责任；T14 的已接受 v1 不被后来页面 v2 覆盖。

同一身份的角色变化按 R §4 的跨交易语境分析：可在一处作为 Provider，在另一处作为 Buyer 或 Payer；身份引用保持连续，参与角色和授权依据分别解释，不设计全局角色字段或新账户流程。评价还须区分购买者、付款人和实际体验者；付款不自动产生服务评价资格。

### 4.3 候选方案

| 候选 | 能暴露的问题 | 不足 |
| --- | --- | --- |
| T01 单 Service | 作为既有流程对照 | 不能充分检验跨域、不同履行和共同采购 |
| T07＋T12＋T14；T04/T05 反例 | 两域、多参与角色、版本、局部变化与追溯；成本可控 | 不能代表全部六域，时间型权益/阶段验收须反证 |
| T04 单 Membership | 续期、多期责任、时间语义 | 单独使用的跨域关联检验不足 |
| T09 Project＋Goods＋Right | 跨域及权利语义覆盖较广 | 复杂度高，失败原因易混杂，不适合作为最小主对象 |

### 4.4 Main Controller 推荐方案（待审稿）

延续 R §16 D12：推荐 T07＋T12＋T14 为最小主对象，T04/T05 为必要反例。后续若单独授权静态概念验证，应只形成可追溯事实图、角色/来源说明和判据逐项回答，不生成 API/DTO/数据库结构，不实现付款或自动退款。D12 本轮仅请 Founder 选择对象、成功和失败判据；不执行该验证。

### 4.5 推荐理由

T07 已具备两个领域、不同 Provider、共同接受、不同履行与局部资金关联；T12 排除“用户全局 Buyer/Payer”，T14 排除“最新 Offering 即历史条款”。T04/T05 进一步检验共同进度是否错误压缩持续权益和阶段责任。该组合沿用 C5 条件性建议，能较小成本提出反证，不需要新的行业调研或提前决定 TX-B/C。

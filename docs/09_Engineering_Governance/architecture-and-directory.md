# 架构与目录治理

> **状态**：Decision v1  
> **Owner**：工程治理  
> **适用范围**：未来所有实现文件

## 架构边界

仓库采用以业务能力为中心的模块化架构。它是一套边界模型，不是要求在应用尚不存在时提前创建空目录。

```text
apps/       应用组合根与可独立运行的应用
applications/ 平台无关的应用用例、编排与 Port
contracts/  跨端 API、错误和协议合同
modules/    业务能力与业务规则
adapters/   外部服务和基础设施实现
packages/   真正跨应用复用的稳定能力
infra/      环境、交付与运行资产
database/   数据迁移和持久化专属资产
scripts/    仓库自动化与治理检查
docs/       产品、工程与执行事实
```

## 当前仓库决策

当前仓库已建立 `apps/prototype`、业务模块和 Adapter 基线。CU-TA-01
进一步建立 `applications/` 与 `contracts/` 的职责契约，但不通过空业务代码
伪造 Application Service 或 API 完成度。

首次加入可运行应用时，必须在 `apps/` 或经明确批准的等价位置建立组合根。首次加入业务代码时，每项业务能力必须有明确归属模块。

## 边界规则

1. `apps/` 负责组合模块，不拥有可复用业务规则。
2. `applications/` 负责平台无关的用例编排、授权和 Port。
3. `contracts/` 负责跨端协议，不拥有业务实现。
4. `modules/` 拥有业务术语、策略和状态转换。
5. Adapter 实现显式 Port；外部 SDK 类型不得泄漏到领域模块。
6. 共享 Package 至少需要两个真实使用方和明确 Owner。
7. 基础设施与数据库资产不得定义产品行为。
8. UI 与传输层通过应用层命令和查询访问业务能力。
9. 产品对象不自动等于数据库表、API 资源、页面或代码类。
10. `utils`、`helpers`、`common`、`misc` 等通用目录不得成为业务规则所有者。
11. 跨边界依赖必须遵循已记录的方向，并由自动化导入检查保护。
12. 边界例外必须登记 `ENG-###`；若改变产品行为，则必须登记 `DEV-###`。
